# Разработка HomeVPN Monitor

GitHub хранит исходники, документацию и задачи. Рабочая среда для сетевых экспериментов — домашний DEV LXC. Локальное графическое приложение Codex на рабочем компьютере управляет DEV через системный OpenSSH. Удалённый Codex CLI и доступ DEV к OpenAI не требуются. См. [ADR 0003](decisions/0003-development-environment.md).

## Среда разработки

- Референсная DEV-среда: Ubuntu Server 24.04 LTS, Linux amd64, непривилегированный LXC. Ресурсы исходной среды: 2 vCPU, 4 ГиБ RAM, 1 ГиБ swap, 20 ГиБ диска. Это не минимальные требования к конечному продукту.
- На рабочем компьютере — локальная копия репозитория, Codex App, системный OpenSSH и авторизация GitHub для записи. Подключение с macOS проверено; на Windows требуется отдельно настроить и проверить свой SSH-ключ.
- DEV доступен по приватному пути (например, через Headscale subnet router). Используй отдельную непривилегированную учётную запись и ключевую аутентификацию. Не передавай приватные ключи или агент SSH на DEV. Системные установки выполняет администратор.
- DEV получает публичный репозиторий через HTTPS без токена записи. Незакоммиченные изменения можно передавать посредством SSH/rsync в отдельную рабочую папку, без секретов и без перезаписи рабочего состояния.
- Go должен быть доступен в неинтерактивном SSH-сеансе. Фиксировать версии Go и Xray-core в документации после проверки прототипа. Не отключать песочницу Codex глобально: разрешать необходимые SSH-команды по отдельности.
- Перед реальными тестами проверять DNS, исходящий маршрут и исключение DEV из правил HydraRoute, особенно после изменения шлюза. Совпадение внешнего адреса в контрольном запросе не доказывает отсутствие выборочной маршрутизации для всех целей.

## Работа над задачей

1. Открой GitHub Issue, уточни критерии приёмки и создай отдельную ветку от main.
2. Работай с синтетическими примерами. При разделении параллельной работы используй отдельные рабочие деревья Git.
3. Для Go-кода после появления модуля запускай форматирование, go vet ./... и go test ./.... Для реальной VPN-проверки используй только домашний DEV LXC.
4. Проверь дифф на рабочие подписки, ключи, адреса, базы и журналы. Укажи в pull request проверенные сценарии и среду выполнения. Слияние выполняет владелец.

## CLI-прототип Xray

Референсная сборка на Linux amd64 использует Go 1.27.4 и [Xray-core v26.11.9](https://github.com/XTLS/Xray-core/releases/tag/v26.11.9). Для архива `Xray-linux-64.zip` сверь SHA-256 `b651f7e1d9966ee2c1b1ee1bf8b52c72771824d3065dce96bbc8bcc19ed95f82`. Бинарник Xray устанавливается отдельно. Команды выполняются из рабочей копии в DEV LXC через `vpn-dev`.

```bash
gofmt -l cmd/homevpn-monitor
go vet ./...
HOMEVPN_TEST_XRAY=/path/to/xray go test -count=1 ./...
go build -o bin/homevpn-monitor ./cmd/homevpn-monitor
```

`gofmt -l` выводит имена файлов, которым нужно форматирование. При заданном `HOMEVPN_TEST_XRAY` интеграционные тесты запускают настоящие процессы Xray, синтетический VLESS/RAW-узел и HTTPS-сервер на loopback.

После проверки SSH, DNS и исходящего маршрута оператор разрешает реальную проверку, размещает конфигурацию на DEV и указывает допустимый HTTPS-адрес. В примере путь к Xray и HTTPS-адрес нужно заменить на значения своей среды.

```bash
bin/homevpn-monitor \
  -xray /path/to/xray \
  -config "$HOME/.config/homevpn-monitor/probe.local.json" \
  -url https://example.invalid/ \
  -timeout 15s
```

Конфигурация должна быть обычным JSON-файлом с правами `0600` вне Git и содержать один VLESS-выход с одним узлом и одним пользователем в формате `settings.vnext` или компактном формате Xray. CLI переносит только настройки выбранного VLESS-выхода и его транспорта. Он создаёт файл `0600` в отдельном временном каталоге и запускает отдельный Xray с SOCKS5 на loopback и случайным паролем. По завершении CLI останавливает Xray и удаляет временный каталог.

Цель проверки — HTTPS-адрес без учётных данных, параметров запроса и фрагмента. Используй путь без секретов. CLI делает один GET через SOCKS5 с проверкой TLS и без перехода по перенаправлениям. При HTTP 2xx строка JSON содержит `status` и `duration_ms` (время до заголовков ответа). При сбое возвращаются `status` и `error_category`. Код выхода 0 означает успех, 1 — ошибку проверки, 2 — ошибку аргументов.

Контрольный прямой запрос выполняется отдельно из DEV к той же разрешённой цели. Если цель возвращает внешний IP, сравнивай адреса внутри DEV и фиксируй только итог сравнения. Совместимость VLESS Reality/XHTTP, gRPC и WS проверяй отдельно. YouTube рассматривай как отдельный сценарий после базового HTTPS-теста, с предварительно согласованной целью.
